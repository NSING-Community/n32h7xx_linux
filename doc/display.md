# LCD 显示与 2D GPU

当前提供 N32H787 HMI 的实验性 LCDC DRM/KMS 驱动、fbdev 兼容入口和
GPU 矩形填充接口，并提供基于上游 libdrm/LVGL 的标准 DRM 与 fbdev 用户态路径。
fbdev 色带、GPU 填充读回、PRIME 扫描输出和翻页已在
800×480 屏上实板验证，像素读回和翻页事件均有记录；屏幕观感仍需目视确认，
驱动超时与分配耗尽路径只有代码审查，没有故障注入证据。

## 构建与显示连接

使用 HMI 板的 RGB LCD 接口及示例对应的 800×480 屏幕。电脑端在项目根目录运行：

```sh
make kernel
make display-test
```

第一条生成内核和设备树；第二条生成板端验证程序
`out/display/n32-display-test`。设备树和内核需要一起更新，具体操作见
[固件更新](ota-update.md)。验证程序按普通文件传到板上可执行的位置。

显示模式与 GPU 示例一致：RGB565 为默认格式，像素时钟为 AXI÷8；当前 AXI
配置对应 37.5 MHz。水平同步、后沿、前沿分别为 34、46、210，垂直分别为
10、23、22。也支持 XRGB8888 扫描输出，应用必须使用驱动返回的实际 stride。

系统启动时 LCDC 会自动套用这个模式并开始扫描 fbdev 的帧缓冲。本板控制台在
串口上，没有 fbcon，所以屏幕上电后是稳定的黑色；这不表示显示驱动没有起来，
只有向 `/dev/fb0` 写入后才会出现内容。

LCD 与 GPU 共用 4 MiB 预留 DMA 内存，该部分不能再用于普通应用。相机采集池
与其独立。分配按页及连续块取整，4 MiB 池不代表应用可同时分配任意组合的
4 MiB 图像；需要计入 fbdev 和 GPU 命令缓冲区。800×480 RGB565 单块缓冲区
为 768000 B，实际占 1 MiB；XRGB8888 单块为 2 MiB。当前 DRM/LVGL 的双缓冲
RGB565 加上 fbdev 控制台约占 3 MiB，因此 4 MiB 是常用组合的下限附近，不是
可以任意挥霍的余量。每块 GEM 缓冲区还需要一份同尺寸的普通内存作为 shmem
后备，这部分不计入 4 MiB 图形池。

## 不预留显示内存

不需要 LCD 或 GPU 时，可以关闭显示设备并把 4 MiB 图形池交回 Linux。默认仍然
预留；需要在电脑端构建时显式指定：

```sh
make LCD=0
```

这个选项选择 `out/kernel/n32h787-hmi-no-camera-no-display.dtb`（默认同时关闭
摄像头），不会修改已有的内核配置。也可以只关闭显示、保留摄像头：

```sh
make CAMERA=1 LCD=0
```

关闭后 LCDC、GPU、面板、背光和图形内存池都不会注册，启动后不会出现
`/dev/fb0` 或 `/dev/dri/cardN`；正常情况下 `MemTotal` 会比默认 DTB 增加约
4096 kB。图形池和相机采集池在物理地址上紧贴主 RAM 顶部排列，关闭哪一个，
释放的区间就直接并入主 RAM，不会留下夹在两个保留区之间的小块。它不会改变
相机采集池、默认 DMA 池或 `system` 分区。切换 DTB 后必须
重启；使用网络更新时可执行 `make ota-dtb LCD=0 H787_BOARD=root@<板子IP>`。
不传 `LCD` 时仍为 `1`，现有显示配置不受影响。

## 板端验证

先确认当前设备路径，不假定 DRM 卡的编号。板端执行：

```sh
ls /dev/fb* /dev/dri/*
```

LCDC 的 DRM 驱动名为 `n32h7xx-lcdc`，GPU 的为 `n32h7xx-gpu`。可以通过
`/sys/class/drm/` 下设备的 `device/driver` 链接区分它们。下面命令中的尖括号
内容均需替换为已确认的设备路径，程序路径按实际上传位置调整。

先停止其他会写屏幕的应用，然后测试 fbdev。最后一个参数是保持时间，可省略，
默认 5 秒：

```sh
./n32-display-test fb '<FB_DEVICE>' 10
```

屏幕应显示白、黄、青、绿、品红、红、蓝、黑八条竖向色带，保持后恢复原先的
帧缓冲内容。需要目视检查颜色、位置、稳定性；程序返回成功只能说明内存写入
完成，不能证明屏幕正常。

接着验证 GPU、共享缓冲区和扫描输出：

```sh
./n32-display-test gpu '<GPU_RENDER_DEVICE>' '<LCDC_DRM_DEVICE>' 10
```

程序检查 RGB565 和 ARGB8888 填充结果、行间空隙与缓冲区保护区域，拒绝越界
参数；随后由 GPU 画出一整帧 800×480（蓝底白边），经 PRIME 导入 LCDC 并翻页
显示，再翻回原帧缓冲。最后一个参数是保持秒数，可省略，默认 10 秒，填 0
适合批量运行。屏幕出现蓝底白边即说明 GPU 绘制、共享缓冲区和 LCD 取数三者都
正常。输出中两项读回和一项扫描输出各打印一条 `PASS`。

复制与格式转换的自检（不显示到屏幕，只读写 GPU 缓冲区）：

```sh
./n32-display-test blit '<GPU_RENDER_DEVICE>' 800 480 30
```

程序在源缓冲区写入图案、把目标涂成标记值，然后逐像素核对整屏 1:1 复制、
带偏移和行距的窗口复制、`RGB565`、`XRGB8888`、`ARGB8888` 之间的互转，以及
越界和非法参数是否被拒绝；随后再跑一组几何用例（2:1 缩小、1:2 放大、
3:2 缩小、90/180/270 度旋转、两个方向的镜像、旋转加缩放），每一组都与 CPU
算出的参考逐像素比较，并检查目标边界外的像素没有被写过。最后一个数字是
整屏复制的重复次数，用于给出平均耗时。整屏复制需要两块同尺寸缓冲区，内存
紧张时先用小尺寸确认功能。

几何用例之后还会输出一行类似 `full 640x360 RGB565 rotate 90: 16.20 ms` 的
计时，表示同尺寸整幅 90° 旋转的平均耗时。90°/270° 现在与普通 1:1 拷贝处于
同一量级；数字会随 SDRAM、LCDC 扫描和 SSH 负载浮动，同一次会话内比较即可。

翻页和垂直同步单独测试：

```sh
./n32-display-test flip '<LCDC_DRM_DEVICE>' 1 10
```

程序先测 16 帧 vblank 的时间与序号，再翻到新缓冲区保持 10 秒后翻回，每次
翻页都等待完成事件并检查序号递增。屏幕应出现蓝底白边和一条自左上到右下的
白线；线被斜切或边框缺边说明 stride 或时序不对。第一个数字是翻页对数，
第二个是保持秒数，可省略，默认 5 秒。压测时把保持设成 0：

```sh
./n32-display-test flip '<LCDC_DRM_DEVICE>' 300 0
```

每次测试结束都会翻回原帧缓冲，出错时也会尝试恢复。若屏幕仍停在测试画面，
重启开发板即可恢复（此时 LCDC 仍在扫描测试缓冲区，写 `/dev/fb0` 不会显示）。

## 帧率

800×480 RGB565、系统空闲时的实板测量；驱动按 vblank 翻页，所以面板刷新率
就是帧率上限：

| 项目 | 实测 |
| --- | --- |
| 面板刷新 | 64.31 Hz（15.55 ms/帧） |
| 纯翻页（不重绘） | 64 fps |
| GPU 每帧整屏填充 + 翻页 | 61.0 fps（300 帧中 10 帧未更新） |
| GPU 整屏填充，RGB565 | 9.5–9.7 ms，38–41 Mpixel/s，77–81 MB/s |
| GPU 整屏填充，XRGB8888/ARGB8888 | 17.9 ms，21 Mpixel/s，83–86 MB/s |
| GPU 整屏纯色矩形 / 填充，RGB565 | 9.35 / 9.63 ms，82.1 / 79.8 MB/s |
| GPU 整屏复制（1:1），RGB565 | 22.4 ms，68.6 MB/s（读+写） |
| GPU 复制 2:1 缩小 / 1:2 放大，RGB565 | 与同面积 1:1 同量级（792×464 与 396×232 互转） |
| GPU 旋转 0/180 度、单向镜像，RGB565 | 与 1:1 同量级，800×480 约 22 ms |
| GPU 旋转 90/270 度，RGB565 | 800×480 约 39.8 ms（400×240 按面积约 10 ms） |
| GPU 整屏混合，RGB565 | 640×360 约 13.5 ms，68 MB/s（读+写） |
| GPU 整屏凸多边形（AA / no-AA），RGB565 | 17.3–17.8 ms，86–89 MB/s（读+写） |
| GPU 整屏填充贝塞尔曲线（AA / no-AA），RGB565 | 640×360 约 5.0 ms |
| CPU 32 位写整屏 | 175 MB/s，227 fps |
| 关掉面板输出后的 GPU 填充 | 9.6 ms，与扫描时相同 |

- 37.5 MHz 像素时钟、800×480、总时序 1090×535 定出 64.31 Hz；改分辨率或
  时序会同步改变上限，改不了驱动里的翻页节奏。
- 纯翻页差的那不到 1 fps 来自事件唤醒和进程调度。翻页请求只要在下一次
  vblank 之前发出就在那次 vblank 生效，实测 vblank 后 14 ms 提交仍能赶上；
  错过就要等下一帧，所以应用应在一帧内尽早提交。
- GPU 整屏填充中位 9.5–9.7 ms，p99 12–22 ms、最差 19–32 ms，具体取决于
  运行时长和后台负载。按中位算 60 fps 有余量，按最差帧算会晚一拍。
  关掉面板输出后仍是 9.6 ms；把 LCDC 驱动完全 unbind、彻底没有扫描之后
  还是 9.60 ms，说明扫描输出不抢 GPU 带宽。瓶颈在 GPU 自己的写通路，
  实测约 77–82 MB/s，而 CPU 写同一类内存能到 175 MB/s。
- 32 位格式每字节略快（84–86 MB/s 对 77–81 MB/s），但整帧字节数翻倍，
  所以仍要约 18 ms；RGB565 整屏填充仍是这条通路上最快的选择。
- 不同路径的有效吞吐不一样：纯写填充约 80 MB/s；1:1 复制要读源再写目标，
  每个方向约 34 MB/s。换缓冲尺寸或换一次运行也会有 10–30% 的差异。表中的
  绝对值适合判断量级和比较路径，不要拿不同程序、不同会话之间的几毫秒差异
  当作回归。
- 小矩形主要花在每次提交的固定开销上。驱动在提交后先用 40 µs 有界自旋
  等完成，再退回中断睡眠，1×1 约 35 µs、8×8 约 36 µs、16×16 约 38 µs、
  64×64 约 0.18 ms；320×240 2.2 ms，400×240 2.5 ms。多个矩形应放进一次
  `RECT_BATCH`：128 个 16×16 共 1.54 ms（12.0 µs/个），128 个 1×1 共
  0.42 ms（3.2 µs/个）。单个 1×1 这类的纯色小块仍以 CPU 直接写最快。
- 两个进程同时使用 GPU 会被驱动串行化：各自 320×240 的单次时间从 2.1 ms
  变成约 4.7 ms，总吞吐不变。接口是同步的，没有异步提交或多作业队列，需要
  并行时应自己分时复用同一进程。
- CPU 写整屏 4–6 ms，纯色填充反而比 GPU 快；GPU 的价值是把填充从 CPU 上
  拿下来，以及后续做混合、复制。同步接口下 CPU 会在 ioctl 里等待，若要在
  绘制期间做别的事，需要另起线程或进程。
- 测量在单核 NOMMU 板上通过 SSH 执行，后台活动和 SSH 本身会带来少量抖动，
  重复测量会有几个 fps 的波动。

板端测量命令（帧数可省略，默认 120）：

```sh
./n32-display-test perf '<LCDC_DRM_DEVICE>' '<GPU_RENDER_DEVICE>' 600
```

输出依次给出面板刷新、纯翻页、CPU 整屏填充、GPU 整屏填充、GPU 绘制加扫描
输出，以及 vblank 后不同时刻提交翻页的命中情况。

要复现上面的完整矩阵，包括格式、面积、形状和面板关闭对照：

```sh
./n32-display-test bench '<LCDC_DRM_DEVICE>' '<GPU_RENDER_DEVICE>'
```

单个尺寸反复测量（用于并发对比，两个终端同时运行）：

```sh
./n32-display-test benchfill '<GPU_RENDER_DEVICE>' 800 480 300
```

多边形的逐像素验证、非法参数拒绝和整屏性能：

```sh
./n32-display-test poly '<GPU_RENDER_DEVICE>' 800 480
```

贝塞尔曲线的几何、覆盖率、alpha 和两种目标格式：

```sh
./n32-display-test curve '<GPU_RENDER_DEVICE>' 640 360
```

八种像素格式的填充、颜色转换、混合拒绝和复制往返：

```sh
./n32-display-test formats '<GPU_RENDER_DEVICE>'
```

每个格式依次检查：`FILL` 写入的原始像素逐像素正确；`RECT` 把 ARGB8888 颜色
按格式截断后写入、矩形外不被改动；`BLEND` 对该格式返回成功；`BLIT` 同格式
往返的 RGB 通道不变、alpha 被写成 1.0，再从该格式复制到 `RGB565` 并核对通道
位置。最后一行 `formats: 0 failing cases` 表示全部通过。

`BLEND` 的数值正确性由 `blend` 测试单独覆盖：`RGB565`、`XRGB8888` 和
`ARGB8888` 各跑 48 组 alpha/颜色组合，逐像素与软件 source-over 参考比较；
`ARGB4444`/`ARGB1555` 另做 alpha 字段的定点检查。`blit` 测试里另有
`blit blend …` 三组：1:1、2× 放大和 90° 旋转，源和目标都带逐像素 alpha，
同样逐像素比对；并检查不透明复制仍然把 alpha 写成 1.0、`RGB565`/`XRGB8888`
源在合成模式下返回 `EINVAL`。

硬件计数器给出的是像素数、写入数和时钟数，不受 CPU 测时和 SSH 负载影响：

```sh
./n32-display-test profile '<GPU_RENDER_DEVICE>' 640 360 4
```

输出 `profile pixels: ok`、`profile counters off: ok` 和 `profile: PASS`
表示像素数与宽×高×次数一致、关闭的计数器读回 0、绘制结果正确。第一行的
`pixels`/`writes`/`clocks` 就是四个计数器的值，`clocks` 后面的括号是除以
重复次数后的单次开销。随后还会检查非法参数：重复 0 次、次数超出上限、事件号
70、宽度 0 都必须返回 `EINVAL`，被接受就判定失败。

性能数字只有在真的写完时才可信。`verify` 先用 CPU 把整块缓冲涂脏，再由 GPU
填充，最后逐像素核对，所以残留的旧数据不会被当成填充结果：

```sh
./n32-display-test verify '<GPU_RENDER_DEVICE>' 800 960
```

## 兼容性

`compat` 会走过一遍接口边界，逐项打印 `PASS`/`FAIL`：

```sh
./n32-display-test compat '<LCDC_DRM_DEVICE>' '<GPU_RENDER_DEVICE>'
```

已验证的行为：

- GPU 注册完整卡节点（例如 `/dev/dri/card1`）和渲染节点
  （`/dev/dri/renderD128`）两个入口。创建缓冲、填充和绘制在两者上都可用；
  渲染节点适合纯渲染应用，它会拒绝 `MODE_GETRESOURCES`、`SET_MASTER` 和
  `MAP_DUMB`（`EACCES`）。卡节点接受 `SET_MASTER` 和 `MAP_DUMB`，
  `MODE_GETRESOURCES` 返回 `EOPNOTSUPP`，因为它没有 CRTC、connector 或
  plane。映射 GPU 缓冲区时用 `CREATE` 返回的 `mmap_offset` 直接 `mmap`，
  两种节点都适用。
- 可填充或画矩形到 `RGB565`、`ARGB4444`、`RGBA4444`、`ARGB1555`、
  `RGBA5551`、`XRGB8888`、`ARGB8888`、`RGBA8888`；复制（`BLIT`）的源和
  目标各自可以是这八种格式中的任意一种；混合（`BLEND`）的目标可以是这八种
  格式中的任意一种；多边形（`POLY`）和曲线（`CURVE`）的目标只接受不带
  alpha 的 `RGB565` 和 `XRGB8888`。
  `RGB888`、`NV12`、`XBGR8888` 和格式 0 都返回 `EINVAL`。未知 handle 返回
  `ENOENT`。
- LCDC 只能扫描 `RGB565` 和 `XRGB8888`；`ARGB8888` 在 `ADDFB2` 就被拒绝。
- 翻页不能改变像素格式（内核 DRM 的通用限制，不是本驱动加的）：显示
  `XRGB8888` 要用 `SETCRTC` 或完整原子提交，不能从 RGB565 直接翻页过去。
- PRIME 两个方向都通：GPU 缓冲区导出给 LCDC 扫描，LCDC 的 dumb 缓冲区也能
  导入 GPU 填充，适合让 GPU 直接画进合成器已有的缓冲。
- 每块 GEM 缓冲区除了占用 4 MiB 图形池，还要一块**同尺寸的连续普通内存**做
  shmem 后备（NOMMU 下由内核预分配）。800×480 RGB565 占 768000 字节，按页和
  连续块向上取整为 1 MiB，即 order-8，所以两个
  800×480 客户端可能同时分配失败，小缓冲区可以并存。分配失败时先释放不用的
  缓冲和映射再重试。
- 接口是同步的纯色填充、纯色矩形、纯色矩形批量、纯色矩形混合、带最近邻
  缩放/旋转/镜像的复制，以及带一像素边缘抗锯齿的凸多边形和贝塞尔曲线填充：
  没有双线性滤波、YUV 或异步提交。返回成功表示硬件作业已经结束。

## 小图元与批量提交

一次 GPU 提交的固定成本（命令流启动、中断、进程唤醒）约 40–60 µs，画多少
像素都要付。逐个小图元调用一次 ioctl 时，这笔成本会压过绘制本身；把一帧里
的矩形合并成一次提交，固定成本只付一次。

批量接口是 `DRM_IOCTL_N32H7XX_RECT_BATCH`。`rects` 指向一个
`struct drm_n32h7xx_rect` 数组，每项和单个 `RECT` 的参数、校验、颜色格式
完全相同；同一次提交里的 `pitch`、`offset`、宽高、颜色和抖动标志可以逐项
不同（`format` 描述的是缓冲区本身，通常整批一致）。数组在绘图开始前复制
进内核，ioctl 返回后可以立即复用。

```c
struct drm_n32h7xx_rect rect[64];
struct drm_n32h7xx_rect_batch batch = {
        .handle = handle,
        .count = n,
        .rects = (uint64_t)(uintptr_t)rect,
};

/* 填好 rect[0..n-1]，每项至少设置 handle、format、offset、pitch、
 * width、height、color；flags 不用的位必须为 0。 */
if (ioctl(gpu_fd, DRM_IOCTL_N32H7XX_RECT_BATCH, &batch))
        perror("RECT_BATCH");
```

限制与行为：

- `count` 为 1–128（`DRM_N32H7XX_BATCH_MAX`），`rects` 不能为空，
  `reserved` 和 `pad` 必须为 0；所有项必须是同一个 `handle`。
- 按数组顺序绘制，整批共用一个 fence，ioctl 在最后一个矩形写完后返回；
  中途参数错误时整批在开始前就被拒绝，不会画一半。
- 只画不透明纯色矩形，alpha 和 `BLEND` 的混合路径不参与；`flags` 的抖动位
  有效，图案仍按每个矩形在缓冲区里的绝对坐标对齐。
- 128 个矩形最多展开约 8.6 KiB 命令流，落在驱动的 16 KiB 命令缓冲内，不会
  因为数量接近上限而截断。

800×480 RGB565、每项尺寸和位置都不同、实板 `batch` 测试的中位时间：

| 每个矩形 | 逐个提交 | 128 个一次提交 | 批量每矩形 |
| --- | ---: | ---: | ---: |
| 1×1 | 35 µs | 0.42 ms | 3.2 µs |
| 8×8 | 36 µs | 0.77 ms | 6.0 µs |
| 16×16 | 38 µs | 1.54 ms | 12.0 µs |

批量之后，耗时主要变成像素写入本身，而不是每次调用的固定开销。只画一个
小矩形时批量没有收益；纯色 1×1 或几个像素的块，CPU 直接写内存仍是纳秒级，
比任何一次 GPU 提交都快。批量适合“一帧几十到上百个脏矩形”的场景，应用应
先合并相邻区域，再用一次调用提交。

## UI 库接入

LVGL 接入采用标准 DRM/KMS 方案：使用上游 LVGL 自带的标准 DRM 后端和上游
libdrm，不增加私有 DRM 封装，也不修改 LVGL 源码。DRM 路径通过标准
`DRM_IOCTL_MODE_CREATE_DUMB` / `MAP_DUMB`、libdrm 的 `drmModeAddFB2`
和原子 KMS 完成显示；LVGL 使用 direct mode，在两个 dumb buffer 中直接绘制，
翻页时等待 KMS 完成事件。不需要 EGL 或 GBM。fbdev 后端仍可使用默认 RGB565
帧缓冲作为兼容路径。触摸或键盘输入需要另外配置输入设备。

当前两种后端都是 **CPU 绘制、LCDC 扫描输出**。GPU 尚未接入 LVGL 的
draw unit，所以使用 DRM 显示不会自动获得 GPU 绘图加速。

### 构建与运行 LVGL 示例

电脑端需要 Meson、Ninja 和 Python 3。项目根目录执行：

```sh
make lvgl-demo
```

产物是 `out/lvgl/lvgl-demo`。源码树中的 `rootfs/usr/lib` 已包含运行时
`libdrm.so.2`；如果重新构建 libdrm 或更新版本，再执行：

```sh
make install-libdrm
make rootfs-squashfs
```

把验证程序复制到板上可执行的位置并运行。下面以 `/system/bin` 为例，设备路径
按前面确认的结果替换；不假定 DRM 卡一定是 `card0`：

```sh
scp out/lvgl/lvgl-demo root@<BOARD_IP>:/system/bin/
ssh root@<BOARD_IP>
lvgl-demo -d '<LCDC_DRM_DEVICE>' -t 20 -r 16
```

`-r 16` 把 LVGL 刷新周期设为 16 ms；省略时使用库内默认值。`-s` 在每个周期
强制重绘整个屏幕，`-t 0` 持续运行到按 Ctrl-C。程序每秒打印一次渲染帧率、
flush 次数和运行时间，退出时打印内存与 CPU 时间。`flush/s` 是提交显示的次数，
不等于面板刷新率。

fbdev 兼容路径把设备换成帧缓冲节点：

```sh
lvgl-demo -d /dev/fb0 -t 20 -r 16
```

满屏重绘压力测试：

```sh
lvgl-demo -d '<LCDC_DRM_DEVICE>' -s -r 5 -t 30
```

800×480、RGB565、系统空闲时的实板基线：

| 路径 | 测试 | 实测 |
| --- | --- | --- |
| fbdev | 普通动画，`-r 16` | 33–39 fps |
| DRM | 普通动画，`-r 16` | 33–39 fps，约 64–68 flush/s |
| fbdev | 满屏重绘，`-s -r 5` | 16–20 fps |
| DRM | 满屏重绘，`-s -r 5` | 25–32 fps |

DRM 后端一次分配两个 800×480 RGB565 dumb buffer，每个需要 1 MiB 连续内存
（order-8）。NOMMU 下内存碎片化后，即使剩余内存总量还够，也可能无法启动；
程序会明确打印 `DRM_IOCTL_MODE_CREATE_DUMB fail` 和
`DRM buffer allocation failed`。停止其他显示程序、删除不用的 `/tmp` 大文件、
释放缓存后重试。连续启动和退出十次已通过，没有分配失败。

GPU 提供独立 DRM render node，接口定义见
`kernel/include/uapi/drm/n32h7xx_drm.h`。创建 GEM 缓冲区后，可执行同步矩形
填充；返回成功表示 GPU 作业完成。需要显示时，通过标准 PRIME 接口将缓冲区
导入 LCDC，再创建 KMS framebuffer。缓冲区格式、pitch 和绘制位置由应用明确
指定，不能传物理地址或任意 GPU 指令。

绘制命令用 `handle`、`format`、`offset`、`pitch` 和宽高指定目标和位置，
`format` 用 `DRM_FORMAT_*` 四字符码，`offset`/`pitch` 以字节计。支持的格式
（每像素 16 位的是 `RGB565`、`ARGB4444`、`RGBA4444`、`ARGB1555`、
`RGBA5551`，32 位的是 `XRGB8888`、`ARGB8888`、`RGBA8888`）：

```text
ARGB4444   A4 R4 G4 B4        XRGB8888   填充字节 R8 G8 B8
RGBA4444   R4 G4 B4 A4        ARGB8888   A8 R8 G8 B8
ARGB1555   A1 R5 G5 B5        RGBA8888   R8 G8 B8 A8
RGBA5551   R5 G5 B5 A1        RGB565     R5 G6 B5
```

上面写的是像素值从高位到低位的分量顺序。32 位格式在小端机器上按字节存放，
所以 `ARGB8888` 在内存里是 B、G、R、A，`RGBA8888` 是 A、B、G、R。

`FILL` 的 `color` 是目标格式的原始像素值（16 位格式取低 16 位，硬件按 16 位
重复写）；`RECT` 和 `BLEND` 的 `color` 始终是 ARGB8888，由硬件转换到目标
格式。默认转换时直接截断低位、不做抖动，需要时可以用 `flags` 打开抖动。

- `FILL` 用清屏单元填充整块矩形，速度最快，不做混合。
- `RECT` 用像素管线画纯色矩形，`color` 是 ARGB8888，**alpha 被忽略**，
  写入的是不透明色；只写矩形范围，不碰范围外的像素。
- `BLEND` 把 `color` 按 DRM KMS 默认混合模式（非预乘 source-over）叠到目标上：
  `out.rgb = src.rgb * A + dst.rgb * (1 - A)`，
  `out.a = A + dst.a * (1 - A)`。目标必须先被读回，速度约为纯填充的一半。
  目标存储 alpha 时该通道一并按上式写入，因此八种格式都可以作为 `BLEND` 的
  目标。
- `BLIT` 从源缓冲区取 `src_width`×`src_height` 的区域，按 `width`×`height`
  输出到目标，可以做最近邻缩放、旋转和镜像，源、目标可以是不同格式（硬件
  做转换）。`src_offset`/`src_pitch` 和 `dst_offset`/`dst_pitch` 分别描述
  两侧，目标和源的每一行都从各自的 `offset` 开始。
  `flags = 0` 时复制不透明：源 alpha 被忽略，目标 alpha 写成 1.0
  （`XRGB8888` 的填充字节写 `0xff`）。置 `DRM_N32H7XX_BLIT_BLEND`（`0x1`）
  则保留采样到的 alpha，按与 `BLEND` 相同的 source-over 叠到目标上：
  `out.rgb = src.rgb*A + dst.rgb*(1-A)`，`out.a = A + dst.a*(1-A)`。
  合成模式要求源格式带 alpha（`ARGB8888`/`RGBA8888`/`ARGB4444`/`RGBA4444`/
  `ARGB1555`/`RGBA5551`）；`RGB565` 和 `XRGB8888` 没有可信的 alpha 值，
  作为合成源返回 `EINVAL`。目标可以是八种格式中的任意一种，逐像素读取目标
  再写回。

缩放是最近邻：每个目标像素取它中心对应的那个源像素，正好落在两个源像素的
边界上时取下标较大的一个，不做插值。所以放大后是硬边，缩小会丢掉部分像素。

`rotation` 用 DRM plane 的旋转编码：`DRM_MODE_ROTATE_0`、`_90`、`_180`、
`_270`（逆时针，分别是 `1<<0`、`1<<1`、`1<<2`、`1<<3`），可以再或上
`DRM_MODE_REFLECT_X`（`1<<4`）或 `DRM_MODE_REFLECT_Y`（`1<<5`）；先旋转
再镜像。90°/270° 时目标的宽高与源对调（源 `W×H` 出图 `H×W`）。多个
`DRM_MODE_ROTATE_*` 位同时置位，或出现这六位以外的位，返回 `EINVAL`。

90°/270° 旋转（包括再叠加镜像）由驱动自动改为按最多 2 像素宽的竖条枚举，使相邻
目标列用到的源行尽量留在纹理缓存里；0°、180° 和单向镜像仍按完整行枚举，
不走竖条。条纹宽度是驱动内部选择，不由 `rotation` 或 `flags` 控制。实测
400×240 从原来的约 105 ms 降到约 12 ms，640×360 约 16–21 ms，与同尺寸 1:1
拷贝同一量级；pitch、SDRAM 与 LCDC 的争用会让耗时上下浮动。

`BLIT` 的源和目标必须是两个不同的缓冲区句柄；同一个缓冲区（包括不同偏移
的自身复制）返回 `EINVAL`，重叠区域请由应用自行分块。`flags` 的其他位必须
为 0。

合成比不透明复制慢，因为它要把目标读回来：`320×180` 的 `ARGB8888` 整帧，
不透明复制约 6.6 ms，合成约 9.8 ms（实板，随内存争用浮动）。小控件用不透明
复制就够；只有确实需要半透明叠加时才付这笔开销。

`POLY` 和 `CURVE` 的目标格式不能带 alpha 通道，只接受 `RGB565` 和
`XRGB8888`：覆盖率混合写进带 alpha 的表面尚未验证，六种带 alpha 的格式
返回 `EINVAL`。`BLEND` 不受此限制。

`RECT` 和 `BLEND` 的 `flags` bit 0（`DRM_N32H7XX_DITHER`）打开混合单元之后
的 4×4 有序抖动。抖动幅度由目标通道位宽自动决定（`RGB565` 为 5/6/5，
`ARGB4444` 等为 4/4/4，`ARGB1555` 等为 5/5/5），作用是把转换时截断丢掉的
低位摊到相邻像素上，适合在 16 位面板上画渐变或照片，代价是纯色区域会出现
轻微颗粒。它只对 16 位目标有效，32 位格式返回 `EINVAL`；`FILL`、`BLIT`、
`POLY`、`CURVE` 没有这个开关，`flags` 的其他位也必须为 0。

抖动图案按缓冲区自身的像素坐标对齐，而不按单个矩形的左上角重新起算，
所以把一块区域分几次重绘（例如按行分块刷新）不会在接缝处出现图案跳变。

`PROFILE` 在同一个矩形上重复绘制若干次，同时用四个硬件性能计数器统计事件，
用来判断一块区域的时间花在哪。矩形、格式、颜色和边界校验与 `RECT` 相同，
绘制本身照常发生；`iterations` 是重复次数，取值 1–30，超过范围返回 `EINVAL`。
每个计数器填一个事件号（0–69），或填 `DRM_N32H7XX_EVENT_OFF` 关闭它。

计数在调用开始时清零、返回前关闭，所以 `counter[]` 只反映这一次调用，也不会
给后面的作业留下运行中的计数器。常用事件：9 可见像素、35 帧缓冲写入像素、
53 流命令数、59 流控制器忙碌周期、69 GPU 时钟。纯色矩形上事件 9 和 35 应
精确等于宽×高×次数，可以用它确认没有多画或漏画；事件 69 除以次数就是单个
矩形的时钟数。事件 69 是“每个时钟周期”，会把 SDRAM 上与屏幕扫描、CPU 访问的
争用一起算进去，同一个调用反复测能差一倍，只适合在同一次会话里做相对比较；
要精确的像素数和写入数请用事件 9 和 35。

`POLY` 填充凸多边形：`vertex_count` 为 3–6，顶点 `x[]`/`y[]` 是相对
`offset` 的 16.16 定点像素坐标，绕向自由，内部取包含顶点质心的一侧。
`color` 是 straight-alpha `ARGB8888`，按覆盖率和 alpha 做 source-over：
`out = src * A * coverage + dst * (1 - A * coverage)`，所以 `A=0` 不改目标。
每个像素的覆盖率由各边距离取两个最小值相乘得到，边上有宽一像素的线性过渡；
`flags` 的 bit 0 置位则关闭抗锯齿，按 `v >= 0` 的阈值判定，边缘是硬边。
目标只支持 `RGB565`、`XRGB8888`，`offset` 要 8 字节对齐，`pitch` 以字节计。
多边形必须完全落在缓冲区内（含抗锯齿过渡带），越界返回 `EINVAL`。

`CURVE` 填充一段二次贝塞尔区域：`(x1,y1)`、`(x2,y2)` 是端点，`(x0,y0)` 是
两端切线的交点，曲线与两条“腿”在这两个端点相切；填充的是控制三角形里
曲线与弦 `(x1,y1)-(x2,y2)` 之间、背离 `(x0,y0)` 的那块，面积正好是三角形的
三分之二。三个点都用 16.16 定点像素坐标（相对 `offset`），`color`、`flags`
和目标格式的要求与 `POLY` 相同，`flags` bit 0 关闭抗锯齿。

曲线本身没有凸性限制，但两条腿的连线必须朝 `(x0,y0)` 一侧鼓出，要求三个
点不共线；反向（凹侧）填充硬件给出的结果不可用，接口不支持，需要时请把
端点或控制点换序后再画。

两条曲线腿有宽一像素的抗锯齿过渡带；弦这一侧按硬边光栅化（硬件在曲线模式
下无法给第三条边做过渡带），边界以像素中心为准。因此沿弦的边缘是 1 像素
阶梯，面积误差上限约为“半个像素 × 弦长”；需要平滑直线边时，把弦放在形状
内部或另用 `POLY` 补边，不要期待它在弦上出现灰阶过渡。

当前 GPU 接口提供凸多边形填充、二次贝塞尔曲线填充与边缘抗锯齿；仍不提供
线条、圆、非凸多边形，也没有 LVGL GPU 绘图后端、SDL 专用后端或
EGL/OpenGL ES 实现。
UI 库使用 DRM 显示不会自动获得 GPU 绘图加速。

90°/270° 的源访问天然是列优先，不能对所有方向都切成竖条：0°、180° 和
单向镜像切成 2 像素竖条会明显变慢（400×240 的 1:1 实测从 6.1 ms 变成
88 ms）。驱动因此只在源坐标沿目标 x 方向换行时启用竖条；应用无需额外配置。

## 故障处理

- 没有显示或 GPU 设备节点：确认使用了对应的新内核和设备树，再查看 `dmesg`
  中 LCDC、panel、backlight、GPU 的探测信息。仅更新内核不能补齐设备树节点。
- 有 fbdev 节点但写入后仍黑屏：屏幕在启动后本来就是黑的（控制台在串口），
  先运行色带测试；仍无显示再检查屏幕供电、排线方向、背光与屏幕型号。不要
  只依据程序退出状态判断接线正确。
- GPU 分配失败：停止占用图像缓冲区的应用、关闭不用的 DRM 文件和映射后重试。
  普通系统剩余内存充足不代表两块连续内存都还够用。
- GPU 填充超时或像素读回不一致：停止 GPU 测试，保留内核错误信息排查。
  超时后驱动尝试复位；复位失败会拒绝后续作业并保留仍可能被硬件访问的内存。
- 翻页报 `Permission denied` 或 `Invalid argument`：确认没有其他 DRM 主控进程
  占用同一张卡，并检查是否在翻页时换了像素格式。翻页失败时程序会尝试翻回
  原帧缓冲；仍停在测试画面时重启开发板。
- 关屏/开屏：`./n32-display-test panel '<LCDC_DRM_DEVICE>' <秒>` 用 `SETCRTC`
  关闭 CRTC、保持指定秒数后恢复原模式和帧缓冲。实板验证正常：关闭后连接器
  为 `disabled`，恢复后画面回到原来的帧缓冲，内核没有
  `drm_atomic_helper_commit_hw_done` 警告，也不再阻塞。需要省电时仍在应用侧
  关闭背光。
- 画面边框四边不一致或斜线被切断：整帧测试把 2 像素白边画在四边，出现这种
  现象说明应用使用的 pitch 与驱动返回的 stride 不一致，应改用驱动给出的值。
